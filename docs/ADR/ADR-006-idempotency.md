# ADR 006: Idempotency Strategy

## Context
In a flash sale, users frantically click the "Buy" button. Network instability may cause clients to retry requests. We must ensure a user doesn't accidentally reserve two items or get charged twice.

## Decision
We mandate an `Idempotency-Key` HTTP header for all state-mutating requests (Reservations, Checkout, Payments).

## Alternatives Considered
- Blindly trusting the frontend to disable the button. (Rejected: easily bypassed, ignores network retries).
- Deduplicating strictly by user ID and product ID. (Rejected: A legitimate user might genuinely want to buy the item again on a separate order later).

## Why We Selected Idempotency Keys
It securely binds the client's *intent* to a unique identifier generated by the client per distinct action. 

## Trade-offs
- **Gained**: Safety against duplicate charges and wasted reservations. 
- **Sacrificed**: Requires storing and checking keys before every mutation, adding a slight latency overhead.

## Consequences
Every mutation endpoint must first check a fast datastore (or unique DB index) for the key. If found, it returns the *previous result* instead of processing the business logic again.
